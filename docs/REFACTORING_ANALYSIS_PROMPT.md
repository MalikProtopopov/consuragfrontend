## КОНТЕКСТ ПРОЕКТА (проверено предварительным аудитом — опирайся, но перепроверяй)

- **Стек**: Next.js 16 (App Router, `output: standalone`), React 19, TypeScript strict,
  TanStack Query v5, Zustand (1 стор — auth), react-hook-form + zod, shadcn/radix (54 компонента в `src/shared/ui`),
  Tailwind v4, axios, recharts, sonner.
- **Архитектура**: FSD — `src/app` → `src/widgets` → `src/features` → `src/entities` (14 сущностей) → `src/shared`.
  Иерархия слоёв **соблюдается строго**, кросс-импортов между entities нет. Не ломай это.
- **Объём**: ~190 файлов, ~28 000 строк. `any` — 0, TODO — 0, тестов — **0**.
- **Слой данных**: единый паттерн `entities/<x>/api/<x>Api.ts` (функции над apiClient) +
  `entities/<x>/model/use<X>.ts` (TanStack Query хуки c query-key factory). Ручных useEffect-фетчей нет.
- **Деплой**: Docker (standalone), nginx, Makefile. Бекенд: FastAPI (есть `docs/openapi.json`, 170KB).
  Сервер маломощный (3.8 GB RAM) — сборка должна оставаться лёгкой.

### Блок A. Декомпозиция страниц-монстров (главный объём работы)

Для **каждой** страницы >350 строк (`find src/app -name "*.tsx" | xargs wc -l | sort -rn`):

1. Прочитай файл целиком. Составь карту: какие хуки данных, какие useState, какие
   диалоги/формы/таблицы, какие inline-компоненты и функции внутри.
2. Определи план разбиения по FSD:
   - переиспользуемые между страницами блоки → `src/widgets/` или `src/features/<домен>/ui/`;
   - специфичные для одной страницы → `_components/` рядом со страницей (паттерн уже
     есть: `admin/requests/_components/PlanRequestDetailDialog.tsx` — следуй ему);
   - выноси не «по 100 строк», а по смысловым границам: один диалог = один файл,
     одна таблица с её пагинацией = один файл, одна форма = один файл.
3. Для каждой страницы запиши в план: целевой список новых файлов с именами,
   что в какой переедет, ожидаемый размер page.tsx после (ориентир: ≤150 строк —
   композиция + роутинг-логика).

### Блок C. Auth и хранение токенов (важно для безопасности — разберись до конца)

1. Прочитай `src/shared/api/apiClient.ts` полностью и `middleware.ts` полностью.
2. Выясни: **кто и когда пишет cookie `access_token`**? (grep `document.cookie`, `cookies`,
   `Set-Cookie`; проверь `withCredentials: true` — возможно cookie ставит бекенд).
   Зафиксируй фактическую схему: что в localStorage, что в cookie, кто их обновляет при рефреше.
3. Определи целевую схему и план миграции. Варианты для оценки:
   - (а) httpOnly cookie от бекенда + middleware как сейчас, убрать localStorage (требует
     правок бекенда — отметь как зависимость);
   - (б) оставить localStorage, но синхронно дублировать в non-httpOnly cookie при
     login/refresh/logout единым модулем `shared/lib/tokenStorage.ts`;
   - выбери реализуемое без бекенда сейчас, второе пометь как «после правок API».
4. Проверь обработку рассинхрона: что происходит, если cookie протух, а localStorage жив

5. Зафиксируй XSS-поверхность: где рендерится пользовательский контент

## ПРАВИЛА

1. **Не предлагай переписывание ради переписывания.** Проект архитектурно здоров
   (FSD чистый, слой данных единообразный) — план должен усиливать существующие
   паттерны, а не вводить новые ради моды.

   точка, но номера строк могли уехать; перепроверяй grep'ом.
3. **Каждая задача — атомарна и независимо проверяема**: после неё `npx tsc --noEmit`,
   `npm run lint` и `npm run build` зелёные, приложение работает.
4. **Учитывай рантайм**: прод собирается в Docker на машине с 3.8 GB RAM — не
   предлагай решений, утяжеляющих сборку (тяжёлые codegen-шаги на каждый build и т.п.;
   codegen — только по ручной команде при изменении openapi.json).
5. Размер задач: лучше 30 маленьких задач, чем 8 огромных. XL-задачи дроби.
6. Декомпозицию страниц планируй **после** создания общих абстракций — иначе
